# i18n & formatting — building for more than one language (load in system + build + states)

Most apps eventually need a second language, and **retrofitting i18n is one of the most expensive
refactors there is** — it touches every string, every layout, and every date in the product. The
decision to make on day one is not "which library"; it is **whether strings live in components or
outside them.** Get that right and adding a language later is a translation job. Get it wrong and
it's a rewrite.

> **This is proportionate.** A single-language internal tool does not need a translation pipeline.
> But *every* app — including that one — should keep strings out of JSX and format numbers, dates
> and currency through `Intl`. Those two habits cost nothing and are the whole retrofit.

---

## 1. The floor, for every app (even monolingual ones)

- **No user-facing string literal inside JSX.** Strings live in a content module (`lib/content/*.ts`
  or a locale file) and components reference keys. This is the same rule as "no hardcoded hex" —
  see `craft-core/references/codebase-hygiene.md`.
- **Never format by hand.** `Intl.NumberFormat`, `Intl.DateTimeFormat`, `Intl.RelativeTimeFormat`,
  `Intl.ListFormat`, `Intl.PluralRules`. They are built in, correct, and free.
- **Money is minor units + an ISO-4217 code** (`data-contract.md`), formatted at the edge:
  `new Intl.NumberFormat(locale, { style: 'currency', currency }).format(cents / 100)`.
  Never `'$' + amount`. Currency symbol placement, separators and spacing all vary by locale.
- **Dates are ISO-8601 UTC in the contract**, formatted for display. **State the timezone in the
  UI** wherever it matters — timezone ambiguity is the #1 source of "this is wrong" tickets.
- **`lang` is set on `<html>`** and updated when the language changes.

## 2. Layout must survive translation

Length changes are not an edge case; they are the normal outcome of translating.

| From English to | Typical growth |
|---|---|
| German | +30–40% (and very long compound nouns) |
| Spanish / French / Portuguese | +20–30% |
| Russian | +15–25% |
| Japanese / Chinese | −20% (but taller line boxes, different wrapping) |

- **Never size a control to its English label.** Buttons, tabs, nav items and table headers must
  grow or wrap gracefully. Test with a pseudo-locale that inflates every string ~40%.
- **Never concatenate sentence fragments.** `"Delete " + count + " items"` is untranslatable —
  word order and pluralization differ. Use one parameterized message per sentence:
  `t('invoices.deleteCount', { count })`, with `Intl.PluralRules` behind it (Slavic languages have
  more than two plural forms; English's two are not the model).
- **Don't build sentences out of UI chrome** — a label that only reads correctly next to its input
  breaks the moment word order changes.
- **Truncation is per-language.** A `line-clamp-1` that fits English may cut German mid-word. Prefer
  wrapping in dense UI, and always pair truncation with a `title`/tooltip.
- **Icons and colour carry culture.** A red/green up/down convention inverts in some markets; a
  "thumbs up" is not universal. Prefer explicit labels over cleverness.

## 3. RTL is a layout decision, not a stylesheet

If Arabic or Hebrew are plausible, build RTL-ready from the start — it costs almost nothing up front
and is a large refactor afterwards:

- **Use logical CSS properties everywhere**: `margin-inline-start` not `margin-left`,
  `padding-inline`, `inset-inline-start`, `border-start-start-radius`, `text-align: start`.
  Tailwind's `ms-*`/`me-*`/`ps-*`/`pe-*`/`start-*`/`end-*` utilities do this — use them by default
  even in a monolingual app, since they behave identically in LTR.
- `dir="rtl"` on `<html>`; the app shell mirrors (sidebar flips side, chevrons flip direction).
- **Do not mirror**: logos, media playback controls, charts with a time axis, or code blocks.
- Numbers stay LTR inside RTL text — let the browser's bidi algorithm work; don't fight it.

## 4. Where it plugs into this pipeline

| Phase | What it owns |
|---|---|
| **ia** | Whether the locale is in the URL (`/es/invoices` — preferred: shareable, indexable, debuggable) or a cookie/header. Which content is translated vs. user-generated. |
| **system** | A type scale that tolerates +40% length; logical properties as the default; a font stack with the glyph coverage for every target script (Latin-only faces fail badly on Cyrillic and CJK). |
| **contract** | Locale-independent data: minor units + currency code, ISO timestamps, **enum keys not labels** (`status: 'overdue'`, never `'Vencida'` — the label is a UI concern). |
| **screens** | Message keys, not sentences, in the specs. |
| **states** | Empty and error microcopy as parameterized messages. |
| **polish** | Verify with the inflated pseudo-locale and, if applicable, `dir="rtl"`. |
| **review** | The long-language stress test (`states-and-edges.md` §5) is measured, not imagined. |

## 5. Library choice — only after the above

The habits matter more than the tool. When a second language is actually in scope, in a Next.js App
Router project the locale belongs in the route segment (`app/[locale]/…`) with `next-intl` or
`next-intlayer`; server components read messages server-side so translations don't ship to the
client wholesale. **Do not install an i18n framework for a monolingual app** — that is scaffolding
nobody asked for. Keep the strings outside JSX and the retrofit stays cheap.

## The i18n gate (review verifies, when i18n is in scope)

1. No user-facing string literal inside JSX.
2. No concatenated sentence fragments; plurals go through `Intl.PluralRules`.
3. All numbers, currency, dates and relative times formatted via `Intl` with an explicit locale.
4. Layout holds at +40% string length on every screen, at 320px.
5. Logical CSS properties throughout; `dir="rtl"` renders correctly if RTL is in scope.
6. `lang` set and updated; the locale is reflected in the URL if it's a routed concern.
