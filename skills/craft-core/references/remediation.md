# Remediation — rescuing a codebase that was built badly (load in audit + remediate)

Sometimes the project already exists and it is **bad**: generated by an AI in one shot, or grown
without discipline. Duplicated components, hardcoded values everywhere, dead files nobody dares
delete, `any` as a type system, no states, no boundaries, real bugs. The ask is: *analyze it module
by module, page by page, component by component, and make it right.*

This is a **different mode from adopting**, and confusing the two is the single most expensive
mistake available here.

---

## 1. Rescue INVERTS the adopt rule — but only after you judge

> **Adopt:** *"You are a guest — match the project, don't impose."*
> **Rescue:** *"The project's conventions are the disease. Matching them propagates it."*

Both are correct in their context, so **the first act of a rescue is a verdict, not a refactor.**
You do not get to decide "this is bad, I'll rewrite it" by taste. You assess, you score, and the
score decides.

### The health assessment (score each, 0–3)

| Dimension | 0 — Sound | 3 — Broken |
|---|---|---|
| **Type safety** | strict TS, no `any` | `any` everywhere, `@ts-ignore`, or no TS |
| **Duplication** | one Button, one Header | the same markup pasted across screens |
| **Hardcoding** | tokens single-sourced | hex/px/URLs/strings inline everywhere |
| **Architecture** | logic in `lib`, clear boundaries | business logic inside JSX, god components |
| **Dead weight** | none | unused files, exports, deps, routes, env vars |
| **States** | every screen complete | only the happy path |
| **Security** | validated, headers, no secrets | unvalidated public endpoints, secrets in the client |
| **A11y** | keyboard + AA measured | div-buttons, no focus, colour-only state |
| **Correctness** | no known bugs | reproducible bugs in normal use |
| **Visual craft** | intentional and consistent | inconsistent, broken responsive, the kit look |

### The decision, from the score

| Total | Verdict | What you do |
|---|---|---|
| **0–8** | Healthy | **Adopt.** Match conventions, add your work, report the rest. |
| **9–18** | Salvageable | **Rescue.** Establish YOUR conventions at the root, migrate everything to them in waves, delete what they replace. This is the normal rescue. |
| **19–26** | Severe but structured | **Rescue, staged.** Same, but expect several sessions; ship wave by wave, each independently valuable. |
| **27–30** | Beyond repair | **Say so.** A rewrite is cheaper than a rescue. Present the evidence and the comparative cost — do NOT start a refactor you know is the wrong shape of work. |

**Being honest at the top of that table is part of the job.** An agent that grinds through a
hopeless remediation because it was asked to is not being helpful — it is burning the user's time
to avoid an uncomfortable sentence. Say it plainly, then offer the rewrite path.

**Per-dimension override:** security holes and reproducible bugs get fixed **regardless of the
verdict**, immediately, even in an otherwise-healthy project. A leaked key doesn't wait for a wave.

## 2. Never refactor without a safety net — build it FIRST

A rescue changes code that nobody has tests for. Without a way to detect breakage, "improvement"
is indistinguishable from silent regression. **Wave 0 is always the safety net**, before a single
line is improved. Full method in `safety-net.md`; the short version:

1. `tsc --noEmit` (turn strict ON — it will scream; that list IS your bug backlog)
2. lint + build both green
3. **Route smoke tests** — every route renders, no console errors, no failed requests
4. **Visual baselines** — Playwright screenshots of every page × viewport × theme, committed as
   the reference. This is how "it still looks right" becomes *measured* instead of claimed.
5. Characterization checks around any non-trivial logic you're about to move

If you cannot build the net for some area, **that area is out of scope for refactoring.** Report it.
Refactoring what you cannot verify is gambling with someone else's product.

---

## 3. The audit — module by module, page by page, component by component

Read-only. Produces the plan. Never changes anything.

**Inventory first** (mechanically, with tools — see `codebase-hygiene.md`):
routes/pages · modules/features · components (and their duplicates) · `lib`/utils · data access ·
dependencies · env vars · assets · styles.

**Then judge each unit** against a fixed checklist, so nothing is judged by mood:

```
component: src/components/InvoiceTable.tsx        (412 lines)
  used by:      2 routes  ·  duplicated in: components/BillingTable.tsx (89% similar)
  types:        4× any · 1× @ts-ignore (no reason)
  hardcoded:    11 hex · 23 px · 1 API URL · 6 magic numbers
  architecture: fetch + sort + currency formatting inside the component body
  states:       happy path only — no loading, no empty, no error
  a11y:         <div onClick> rows · no aria-sort · focus invisible
  bugs:         sorting by amount sorts lexically ("1000" < "9") — REPRODUCED
  verdict:      REPLACE at root → one <DataTable> primitive; delete both files
  risk:         medium (2 call sites)   ·   wave: 3
```

Every finding needs **evidence** (a path, a line, a tool output, a reproduced failure). A finding
you can't point at is an opinion, and opinions don't earn a refactor.

**Also audit what ISN'T there** — the gaps are findings too: missing states, missing routes/
boundaries, missing validation, missing env typing, missing error handling, missing keyboard paths.

---

## 4. The waves — order is not arbitrary

Refactoring everything at once in an untested repo is how you produce a broken app and an
unreviewable diff. Go in waves, **highest leverage and lowest risk first**, verifying between each.

| Wave | What | Why here |
|---|---|---|
| **0 · Safety net** | strict TS on, lint, build, smoke tests, visual baselines | Nothing after this is safe without it |
| **1 · Delete dead weight** | unused files, exports, components, routes, deps, env vars, CSS | **Highest leverage:** every later wave gets cheaper because there is less code. Never refactor something you're about to delete |
| **2 · Tokens** | extract the real palette/scale, replace every hardcoded value | **Tokens move every screen at once.** One wave kills "quemado" globally |
| **3 · De-duplicate** | collapse repeated markup into real primitives; one Button/Header/Table | Now that dead code is gone, the true duplication set is visible |
| **4 · Architecture** | logic out of JSX into `lib`, data behind a contract, boundaries, split god files | Structural — needs waves 1–3 done or you restructure garbage |
| **5 · Correctness & completeness** | reproduce and fix bugs, add every missing state, validation, error handling | Now the code is legible enough to fix correctly |
| **6 · A11y & craft** | keyboard, focus, ARIA, measured contrast, responsive, density, type | The polish pass, on a codebase that can now hold it |
| **7 · Performance** | bundle, code-split, client/server boundaries, N+1, images | Last: optimizing code you were about to delete or rewrite is waste |

**Between every wave:** `tsc` + lint + build + smoke + **visual diff against the baseline**, then
commit that wave alone. A wave that can't be verified doesn't get merged into the next one.

**Update the baseline deliberately.** When a wave *intentionally* changes appearance (wave 6),
re-record the baselines and say so in the report — never let an intended change silently mask an
unintended one.

## 5. Guardrails — a rescue is surgery, not enthusiasm

- **Work on a branch.** Never remediate directly on `main`.
- **One wave, one commit** (or a tight series). Every wave must be independently revertible. This
  is what makes a large refactor reviewable — see the `work-unit-commits` and `chained-pr` skills.
- **Never delete without proof.** Tool output *and* a grep, and check for the things static
  analysis misses: dynamic imports, string-based route references, CSS selectors used by markup
  the analyzer can't see, anything reached by reflection, and the public API of a package.
  **Uncertain = don't delete; report it.**
- **Change at the ROOT.** When you replace an approach, delete what it replaced in the SAME wave
  and refactor every caller. Half-migrations — old and new coexisting — leave the codebase *worse*
  than you found it, because now there are two ways to do everything.
- **Never leave a wave half-done.** Finishing wave 2 for 80% of the app is not 80% of the value;
  it's a new inconsistency. Scope the wave to what you can complete.
- **Fix what you find, even if nobody mentioned it.** A bug, a security hole, a broken edge case,
  a dead link — it gets fixed on the spot. That is the zero-debt rule; it applies to inherited code
  exactly as it applies to code you wrote.
- **Don't gold-plate.** Rescue means "correct, clean, scalable" — not "rewritten to my taste".
  A convention that is merely *different* from yours but consistent and sound stays.
- **Behaviour is preserved unless it's a bug.** A refactor that changes what the product does is
  not a refactor. If you believe a behaviour is wrong, that's a finding — raise it, don't silently
  "fix" it.

---

## 6. The report — what the user gets

Rescues must be legible, or they read as "the agent changed 4.000 lines and says it's better."

- **The verdict** — the health score per dimension, and what it implied.
- **The inventory** — what exists, what was dead, what was duplicated.
- **What changed, per wave** — with counts (files deleted, values tokenized, components collapsed,
  bugs fixed, states added) and the commit for each.
- **The evidence** — before/after on every gate: `tsc` errors, lint, bundle size, dead-code tool
  output, contrast measurements, the **visual diff result per page**.
- **The bugs found and fixed**, each with how it was reproduced.
- **What you did NOT touch, and why** — out of blast radius, unverifiable, or a behaviour question
  for the user. This section is not optional; it's what makes the rest trustworthy.
- **What remains** — honestly, with severity. A rescue that claims total victory is a rescue
  nobody should believe.
